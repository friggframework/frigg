# ADR-050: Move to osls 4 for 2.0.1

**Status**: Accepted
**Date**: 2026-10-02
**Deciders**: Sean Matthews

## Context

Frigg deploys and runs apps through [osls](https://github.com/oss-serverless/osls), the
MIT-licensed continuation of Serverless Framework v3. `frigg start`, `frigg build` and
`frigg deploy` spawn the `osls` binary (`frigg-cli/start-command/index.js:47`,
`build-command/index.js:22`, `deploy-command/index.js:15`). The composed definition from
`infrastructure-composer.js` is what osls validates and packages.

### Where Frigg is today

- `packages/devtools/package.json:64` (devDependency) and
  `packages/devtools/frigg-cli/package.json:29` (dependency) pin `osls: ^3.58.0`. Open PR
  #639 raises this to `^3.78.0`, and adds the section *"Why osls 3 and not osls 4"* to
  `docs/reference/aws-sdk-v3-osls-migration.md`, which this ADR replaces.
- The lockfile resolves osls `3.76.0`. osls 3 depends on `aws-sdk ^2.1693.0`, so every Frigg
  app installs the end-of-support AWS SDK v2 through its deploy tool.

### What npm says (checked 2026-10-02)

| dist-tag | version | published | engines.node |
|---|---|---|---|
| `latest` | 4.4.0 | 2026-09-25 | `^20.19.0 \|\| ^22.13.0 \|\| >=24` |
| `legacy` | 3.78.0 | 2026-09-06 | `^20.19.0 \|\| ^22.13.0 \|\| >=24` |

osls 4.0.0 shipped on 2026-07-01. Since then every 3.x release has gone out alongside a
4.x release. The osls README says the 3.x branch "continues to receive bug and security
fixes". New capabilities go only to 4.x: AWS SDK v3 internals, IAM Identity Center (SSO)
credentials, `AWS_ENDPOINT_URL` endpoint overrides, `provider.pruneFunctionVersions` and
Lambda durable functions.

### Why decide now

- **2.x is a new major line, and 2.0.1 is its first patch release.** Few apps run 2.x in
  production yet, so this is the cheapest point to change the deploy tool. If we wait, we
  must either ship a breaking infrastructure change later in 2.x, or hold the change for
  3.0 and stay on the `legacy` tag for all of 2.x.
- **The gap is small and fully known.** Two things in Frigg's composed definition fail
  osls 4 validation (below). We already converted both in a scratch wrapper and ran a
  scaffolded app end to end, so this is not an open-ended port.
- **osls 3 keeps SDK v2 in every app's tree.** Moving to 4 removes the largest SDK v2
  dependency that Frigg brings in. `serverless-offline-sqs` still uses SDK v2 as its own
  dependency (see the plugin matrix).

### What breaks on osls 4.4.0

From the osls [Upgrading to v4](https://github.com/oss-serverless/osls/blob/main/docs/guides/upgrading-to-v4.md)
guide, checked against what Frigg emits:

| osls 4 breaking change | Affects Frigg? |
|---|---|
| `package.include` / `package.exclude` rejected at service, function and layer level; use `package.patterns` | **Yes.** Every core and builder function emits them (inventory below). |
| Invalid config fails by default (`configValidationMode: error`) | **Yes.** This turns the two schema problems into hard failures. On osls 3 they were only warnings. |
| `useDotenv` must be `true` if present (`config-schema.js`: `useDotenv: { const: true }`) | **Yes.** `useDotenv: false` is emitted for every non-offline command. |
| `frameworkVersion` pinned to a v3 range fails with `FRAMEWORK_VERSION_MISMATCH` before validation | No for Frigg's defaults: `'>=3.17.0'` and logging's `'>=3.58.0'` both match 4.x. **Yes** for apps that set `'3'` or `^3.x`. |
| Plugin entries validated (lowercase npm names or `./` paths) | No. All Frigg plugins are valid npm names. |
| AWS SDK v2 surfaces removed (`provider.request`, `provider.sdk`, `provider.getCredentials`) | No for loaded plugins (matrix below). |
| `variablesResolutionMode: 20210219`, `console`, `provider.lambdaHashingVersion`, `provider.eventBridge.useCloudFormation` removed | No. Frigg emits none of them. |
| Function `condition` applies to companion resources | No. Frigg emits no function `condition`. |
| Top-level provider IAM settings deprecated (`PROVIDER_IAM_SETTINGS_V3` warning, removal in osls 5) | Warning only. Frigg emits `provider.iamRoleStatements` (`base-definition-factory.js:185`, `infrastructure-composer.js:113`). |
| Credential resolution uses SDK v3 semantics (`~/.aws/config` always merged, `mfa_serial` honoured, SSO supported) | Operator-facing. The deploy identity can change for some profile layouts. |
| AWS request changes: SDK v3 retries, no global concurrency cap, regional STS, CRC32 S3 checksums, AWS error codes renamed, `AWS_ENDPOINT_URL*` honoured | Operator-facing. The Frigg CLI does not parse osls error codes (checked `deploy-command`, `build-command`, `start-command`). |
| Bundled `dayjs`, `punycode`, `open`, `cachedir`, `object-hash`, `require-from-string` removed | No Frigg code relies on them through osls. |

### Evidence from the scratch run

With osls 4.4.0 in a scaffolded app, after we converted E1–E6 and U1 in a scratch
`infrastructure.js` wrapper:

- `frigg start` returned `GET /health` 200, user create and login 201, and
  `GET /api/integrations` 200.
- `frigg build --stage prod` packaged against moto. osls 4 honoured `AWS_ENDPOINT_URL`.
- The converted function zips were about 73 MB each. **We did not compare them to an osls 3
  baseline.** This is the main open risk, and the verification plan addresses it.

## Decision

**Frigg 2.0.1 targets `osls ^4.4.0`.** Frigg stops emitting configuration that osls 4
rejects. The change ships in two steps so that each step can be verified on its own (see
Verification).

### 1. Convert `include`/`exclude` to `package.patterns`

Add one helper in `domains/shared/utilities/`, for example `package-patterns.js`:

```js
// Same evaluation order osls 3 applied: excludes first, then includes.
function toPackagePatterns({ include = [], exclude = [] } = {}) {
    return [
        ...exclude.map((p) => (p.startsWith('!') ? p.slice(1) : `!${p}`)),
        ...include,
    ];
}
```

E1, E3, E4, E5 and E6 build `{ patterns: toPackagePatterns({ include, exclude }) }` and keep
`individually` where it is set now. The exclude and include lists stay the same. Only the
key that carries them changes. Delete E2. Update `nested-node-modules.js` callers through
the helper, not by negating the patterns at the source, so that one place owns the
negation.

**Why this produces the same file set.** Both versions resolve a function's files with
the same algorithm, `resolveFilePathsFromPatterns`:

- osls 3.78.0: `package-service.js:235-238`, `:262`
- osls 4.4.0: `package-service.js:233`, `:253`

The algorithm builds an ordered pattern list, then applies the patterns with
last-match-wins over a candidate list from `glob(['**', ...includes])`. The only
difference between the versions is where function-level patterns go in that list:

| Position | osls 3 with `include`/`exclude` | osls 4 with `patterns` |
|---|---|---|
| 1 | `!` default, config-file, plugin-path, layer and `.env*` excludes | same |
| 2 | `!` function `exclude` (via `getExcludes(funcPackageConfig.exclude)`) | — |
| 3 | service `include` + service `patterns` | service `patterns` |
| 4 | function `include` + function `patterns` | function `patterns` |
| 5 | dev-dependency includes, then `!` dev-dependency excludes | same |

Frigg emits no service-level `include`, `exclude` or `patterns`, so row 3 is empty in both
versions. Function `patterns` = `[!exclude…, include…]` places the excludes at row 4, ahead
of the includes. Rows 2–3 are empty, so this is the same sequence osls 3 produced. osls 3
also handled an exclude that starts with `!` as an include in exclude position, and the
helper keeps that behaviour.

The candidate list is also the same. `lib/utils/glob.js` is byte-identical in 3.78.0 and
4.4.0. Its `buildTasks` applies a negative pattern only to the positive patterns before it.
So `!x` removes files from the `'**'` candidates, but a later positive include (for
example the DocumentDB CA file in E1 and E6) is globbed in its own task and is still found.
A file that `!x` removes from the candidates would also be set to "excluded" by `!x` in the
osls 3 list.

The patterns syntax is valid on osls 3 too (3.x accepts `patterns` at function level). So
this step can merge and be verified **before** the version bump.

### 2. Emit `useDotenv` only when it is `true`

Replace U1 with `...(process.argv.includes('offline') && { useDotenv: true })`. osls 3 and
osls 4 treat an absent `useDotenv` the same as `false`:

- `cli/conditionally-load-dotenv.js` returns early on a falsy value.
- `package-service.js` adds `.env*` to the excludes only when the value is truthy.

The osls 3 schema is already `{ const: true }`, so `false` only produced a warning there.
`frigg start` keeps loading `.env` and `serverless-dotenv-plugin`. Builds and deploys never
read `.env`. This matches the current intent and the comment at :174.

### 3. Bump the pin and the framework version

- `packages/devtools/package.json` and `packages/devtools/frigg-cli/package.json`:
  `osls: ^4.4.0`.
- Emit `frameworkVersion: '^4.4.0'` from one constant. Today `base-definition-factory.js:169`
  uses `'>=3.17.0'` and `logging-config.js:10` uses `LOGGING_CONFIG_FRAMEWORK_VERSION =
  '>=3.58.0'`. With one constant, an app whose own `package.json` still resolves osls 3
  fails immediately with `FRAMEWORK_VERSION_MISMATCH`, and does not package a different
  artifact without an error.
- Do **not** move `provider.iamRoleStatements` to `provider.iam.role.statements` in 2.0.1.
  App `infrastructure.js` wrappers push into `definition.provider.iamRoleStatements`, so
  renaming the key would break them. In v4 this is only a warning. A later ADR or the osls 5
  work tracks the change.

### 4. Node.js

The Lambda runtime stays `nodejs22.x`. The CLI host must satisfy osls's
`^20.19.0 || ^22.13.0 || >=24`. The root `package.json` declares `node >=22`, which
includes Node 23 and Node 22.0–22.12. **Neither osls 3 nor osls 4 supports these.** Set
`engines.node` to `^22.13.0 || >=24` on `@friggframework/devtools` and
`@friggframework/frigg-cli`, and make the CLI print a clear message when the Node version
is unsupported. Node 20 is outside Frigg's floor already, and it reached end of life in
April 2026.

### 5. Plugin compatibility matrix

Versions are those that the lockfile resolves today. The scan looked for the surfaces osls 4
removed: `provider.request`, `provider.sdk`, `getCredentials`, `variableResolvers` and
`yamlParser`.

| Plugin | Version | Loaded when | osls 4 status |
|---|---|---|---|
| `serverless-esbuild` | 1.57.2 | always | Compatible. It declares `skipEsbuild` as a typed function property. No removed surfaces. |
| `serverless-offline` | 13.10.1 | always (used by `frigg start`) | Compatible. CLI options are typed. No removed surfaces. Its `peerDependencies: serverless ^3.2.0` makes npm install upstream `serverless@3.40.0` beside osls. This is unchanged and harmless, because Frigg spawns `osls` by name. |
| `serverless-offline-sqs` | 8.0.0 | always | Compatible. It uses `aws-sdk/clients/sqs` (v2), which it declares as its **own** dependency, not through osls. |
| `serverless-dotenv-plugin` | 6.0.0 | `offline` only | Compatible. No removed surfaces. |
| `@friggframework/serverless-plugin` | workspace | always | Compatible in the paths it runs. `asyncInit()` → `createLocalStackSQSClient()` (`index.js:103`) calls `require('aws-sdk')`, which is **undeclared** and resolves today only because osls 3 hoists SDK v2. That method is not attached to any hook, so it is dead code. Delete it in the migration, so that a later change cannot attach a hook that breaks on osls 4. |
| `serverless-kms-grants`, `serverless-plugin-monorepo` | 1.1.0, 0.11.0 | not loaded by any builder | Not applicable. |

## Consequences

### Positive

- Frigg is on the supported osls line, with SSO credentials, endpoint overrides,
  `pruneFunctionVersions` and SDK v3 internals. The osls 3 SDK v2 dependency leaves every
  app's tree.
- Step 1 works on both osls 3 and osls 4. The result is that rollback needs only a pin
  change, not a code revert.
- `AWS_ENDPOINT_URL` makes LocalStack and moto builds work without plugin-specific endpoint
  wiring.
- One `frameworkVersion` constant makes a mismatch between the installed osls and the
  version Frigg expects fail at once with a clear error.

### Negative

- **Artifact contents and size are not yet proven equal.** The equivalence argument covers
  the pattern logic. It does not cover dev-dependency detection, symlink handling, or a
  changed default exclude between versions. The ~73 MB zips from the scratch run have no
  v3 baseline. The release is blocked on the artifact diff below. Any difference must be
  explained or fixed before 2.0.1 ships.
- **Apps that customise the serverless config break.** Apps whose `infrastructure.js`
  adds `package.include` / `package.exclude`, sets `useDotenv: false`, pins
  `frameworkVersion: '3'` or `^3.x`, or loads a plugin that uses SDK v2 surfaces now get an
  error on every command. Apps with service-level `package.patterns` see a subtle change:
  osls 3 applied them after function excludes (so they could re-add files), and the same
  patterns now come before the function's own patterns. The function excludes win. The
  release notes and the upgrade guide must list each of these with its fix.
- **This is a breaking change in a patch release.** We accept this for 2.0.1 because 2.x
  adoption is still early (see Context). The `FRAMEWORK_VERSION_MISMATCH` fail-fast and the
  release notes are the mitigation.
- **Operator-facing AWS behaviour changes.** A profile that has static keys in
  `~/.aws/credentials` and a `role_arn` in `~/.aws/config` now assumes the role and can
  deploy into a **different account**. `mfa_serial` prompts, and the prompt fails in CI.
  STS calls go to regional endpoints. A leftover `AWS_ENDPOINT_URL` in a shell sends a real
  `frigg deploy` to the local endpoint. Deploy runbooks and CI need a check.
- **Node 23 and Node 22.0–22.12 hosts can no longer run the CLI.** This was already true
  for osls ≥3.7x, but now `engines` states it.

### Neutral

- Lambda runtime, layers, CloudFormation resource names and IAM statements do not change.
  The deploy tool and the package-config key are the only changes.
- `provider.iamRoleStatements` emits a deprecation warning until a later change moves it.
- ADR-048 §12's floor (`>=3.58.0`) is subsumed by `^4.4.0`.

## Verification plan

Each check is an issue checklist item, and 2.0.1 does not ship until all of them pass.

1. **Unit tests.**
   - `toPackagePatterns` gets table tests that compare its output with the osls 3 ordering:
     `!`-prefixed excludes, an include that re-adds an excluded path, and empty lists.
   - Each builder test (`base-definition-factory.test.js`, `integration-builder.test.js`,
     `migration-builder.test.js`, `admin-script-builder.test.js`) asserts that no function
     has `package.include` or `package.exclude`, and that the expected globs are in
     `package.patterns` in the correct order.
   - A composer-level test walks every function in a fully featured definition (VPC, KMS,
     an integration with webhooks, a queue worker, an extension, migrations, admin scripts)
     and asserts the same.
   - A test asserts that `useDotenv` is absent for `build`/`deploy` argv and `true` for
     `offline`.
2. **Schema check without AWS.** Validate the composed definition for the scaffold and the
   featured app against osls 4.4.0's schema with `configValidationMode: error`
   (`osls print` or `osls package` against moto).
3. **Artifact diff, step 1 (conversion only, osls 3.78.0 for both).** Run `frigg build
   --stage prod` before and after the conversion. Use (a) the scaffold, and (b) an app
   with one integration, a webhook, a queue worker, migrations and admin scripts. For each
   function zip in `.serverless/`, compare the sorted `unzip -Z1` file lists and the
   per-file CRC32 (`unzip -lv`). **Expected: identical.**
4. **Artifact diff, step 2 (osls 3.78.0 → 4.4.0, both converted).** Same apps, same
   comparison. Also compare the CloudFormation templates
   (`cloudformation-template-update-stack.json`) after normalising the artifact hashes.
   Expected: identical file lists. Explain every difference in the PR.
5. **Size budget.** Record zipped and unzipped size per function for v3 and v4. Every
   function must stay under Lambda's 250 MB unzipped limit, with headroom recorded.
6. **`frigg start`** on both apps: `GET /health` 200, user create and login, integration
   list, one queue message processed through `serverless-offline-sqs`.
7. **`frigg build --stage prod`** on both apps against moto (via `AWS_ENDPOINT_URL`) and
   against real AWS credentials.
8. **Real deploy to a sandbox stage** of the featured app:
   - `frigg deploy --stage <sandbox>` succeeds.
   - Invoke each function type once: health, auth, an integration route, a webhook, a
     queue worker, `dlqProcessor` (send a poison message), the DB migration router and
     worker, and an admin script.
   - Then redeploy with no changes. Expected: no function updates.
9. **`frigg doctor <stack>`** on the sandbox stack reports healthy, with no drift.
10. **Docs.**
    - Replace the PR #639 section *"Why osls 3 and not osls 4"* with a pointer to this
      ADR.
    - Add an "Upgrading to 2.0.1" note that lists the breaking customisations and their
      fixes.
    - Update the `frigg` skill and docs that mention `^3.x`.

## Rollback

- **Before 2.0.1 ships:** revert the pin commit (step 3). Steps 1–2 stay, because they are
  valid on osls 3.
- **After 2.0.1 ships:** publish 2.0.2 with `osls: ^3.78.0` and `frameworkVersion` back to
  a range that accepts 3.x. The `patterns` and `useDotenv` output stays, because osls 3
  accepts it. An app that is blocked before a fix can add `"overrides": { "osls": "3.78.0" }`
  and set `frameworkVersion` in its `infrastructure.js` wrapper. The deployed stacks need
  no rollback: resource names and templates do not change (verification step 4).

## Alternatives Considered

- **Stay on osls 3 for all of 2.x (the position in PR #639).** This is safe for 2.0.1, but
  it keeps SDK v2 in every app, keeps Frigg on the `legacy` tag, and makes the same change
  a breaking infrastructure change in a later 2.x release or in 3.0. The gap is two
  emitter shapes, so waiting saves little.
- **Set `configValidationMode: warn` and keep `include`/`exclude`.** This does not work.
  osls 4 removed the keys from packaging (`getIncludes` and `getExcludes` no longer read
  them), so the keys would be silently ignored, and every function would ship its whole
  `node_modules` closure.
- **Support both majors with `frameworkVersion: '3 || 4'`.** Step 1 already makes the
  output valid on both. Advertising both majors doubles the test matrix for no user benefit,
  and it hides an osls version mismatch that should fail.
- **Normalise app-supplied `include`/`exclude` into `patterns` inside the composer.** This
  would hide the change for some apps. But wrappers change the definition *after*
  `composeServerlessDefinition` returns, so the composer never sees most customisations.
  An explicit error with a documented fix is more honest. We can reconsider this if the
  upgrade reports show it is needed.
- **Move to upstream Serverless Framework v4.** This is rejected for the licensing reasons
  already recorded in `docs/reference/aws-sdk-v3-osls-migration.md`.
